# 间隔重复调度方案（dueAt）

## 一、先核对：评审的说法哪些成立

| 评审说法 | 核查结果 | 依据 |
|---|---|---|
| 三档反馈只改 pin / 掌握度，不决定「下次什么时候出现」 | **成立** | `rateWord()` 只写 `opens / lastOpened / pin / mastery`（[index.html L1728-1741](file:///d:/apt/英语单词/mobile/index.html#L1728-L1741)），没有任何「下次到期」字段 |
| 「待复习优先」其实是卡片页打卡，跟记忆曲线无关 | **成立** | `isDue()` = `reviewDone()` 打过 1~3 次卡且未掌握（L1178-1185）；`reviewDone` 读的是 `cards/*.html` 打卡写入的 `<word>_review` |
| 手机端这个维度基本是死的 | **基本成立，而且可见** | 手机刷词页没有打卡入口（只能点「词卡 ›」跳到完整卡页再打卡）；数据页「待复习」直接用的 `isDue`（L2446），绝大多数人这个数字长期是 0 |
| 每天刷的 10 个，明天可能一个都不重复 | **部分成立** | 队列含全部 46 词，重建时按掌握度升序（认识=2 排最后）→ 认识的词确实被推到后面。所谓「3 天后再见」是**词库只有 46 个**带来的副作用，不是调度保证；词库一变大就失效 |
| 已掌握 14 天衰减 | 事实，但它只是把掌握度从 2 降到 1 | `mstRule.decayDays = 14`（L1131、L1159），不排期 |
| 没有输出、没有语境 | 事实，但不是这次要改的 | 属于产品边界，手机端加不了真正的写作/语料 |

结论：**核心缺口是真的**——没有「哪一天该复习哪个词」这件事；但严重程度被夸大了一点：46 个词的规模下，现有的「掌握度排序 + 认识的排尾」已经在做一种粗糙的间隔，只是没有显式日期、不可解释、也扩不动。真正让人难受的是「待复习」这个指标长期是 0。

## 二、方案（最小改动，只补调度）

### 1. 数据字段

在 `store[word]` 里加 `dueAt`（**当天 0 点的时间戳**，不是毫秒级的「此刻 + N 天」）：

```js
function startOfDay(ts){
  const d = new Date(ts);
  d.setHours(0, 0, 0, 0);
  return d.getTime();
}
function rec(word){
  ...
  if(r.dueAt === undefined) r.dueAt = 0;   /* 0 = 从未排期，视为已到期（排在最前） */
  return r;
}
```

- **日期粒度，不是秒级**：D0 晚 11 点点「认识」，若写成 `now + 3 天`，要等到 D3 晚 11 点才算到期，D3 早上打开不出现，用户会觉得「明明三天了」。间隔重复的最小单位就是天，统一用当天 0 点。
- 放 `store` 而不是 `wc_mobile_v1`：掌握度（`opens/pin/mastery`）本来就在这条记录里，调度值跟着走才对；桌面端只增改已知字段，不会抹掉它。
- 旧记录没有 `dueAt` → `0` 视为立即到期，升级当天行为和现在一致；排序上 `0` 比任何日期都小，所以「从未排期」的新词会排在逾期词之前——与现在「未学优先」的观感一致。

### 2. 评级写入间隔（`rateWord`，L1728 附近）

```js
/* 间隔按「天」算，统一落到当天 0 点 */
function dueAfter(level){
  const today = startOfDay(Date.now());
  if(level === 0) return today;                   /* 不认识 → 明天回到到期队列前排 */
  if(level === 1) return today + 86400000;        /* 有点印象 → 明天 0 点 */
  return today + 3 * 86400000;                    /* 认识 → 3 天后 0 点 */
}
```

- **「不认识」的实际效果是「明天回到前面」，不是「今天立刻再刷一遍」**：`buildQueue` 会把今天已评级的词排到队尾，所以它今天不会再出现；跨天后 `dueAt = 昨天 0 点` 算逾期，进到期队列前排。方案早期写的「立即回到前排」与这条现有规则矛盾，以本节为准。
- 行为本身是对的：刚说「不认识」下一秒又见到同一张，体验会很差。
- 方案 A（已选定）：固定三档，简单可解释。
- 方案 B（后续可选）：`认识` 且上次也已掌握时按 3 → 7 → 15 天递进（`r.iv` 记当前档位，答错清零）。多一个字段；46 个词的规模下先不做，跑一周看「到期数是否稳定在 8–12 个」再决定。

### 3. 队列排序（`buildQueue`，L1261-1273）

```js
function buildQueue(onlyFresh){
  const now = Date.now();
  const rated = ratedToday();
  const all = WORDS.slice().sort((a, b) =>
    rec(a.word).dueAt - rec(b.word).dueAt ||        /* 到期早的先刷 */
    masteryOf(a.word) - masteryOf(b.word) ||         /* 同一时刻按掌握度 */
    a.word.localeCompare(b.word));
  const fresh = all.filter(w => !rated.has(w.word));
  const done  = all.filter(w => rated.has(w.word));
  return onlyFresh ? fresh : fresh.concat(done);
}
```

- 到期/未到期不再分两个桶：`dueAt` 升序天然把逾期词排前面、未到期排后面，不会漏刷；`dueAt = 0` 的新词排最前。
- 今天已评级的排到队尾、`onlyFresh` 的语义都不变。
- `shuffle` 与「待复习」不再参与排序；`isDue` 失去用途，删掉（只有队列和数据页两处引用）。
- 三个比较键都定死，同一 `dueAt`、同一掌握度的并列项按字母序，排序结果稳定可复现（46 个词也谈不上性能问题）。

### 4. 数据页「待复习」改成真到期数（L2446）

```js
const t0 = startOfDay(Date.now());
const due = WORDS.filter(w => rec(w.word).dueAt <= t0).length;
```

- 这个数字从此可解释：现在该刷的有几个。
- 已知小瑕疵：今天刚评「不认识」的词会被计入（它确实欠一次，只是今天不再出现），数字和下一张卡会略有出入。想更严格可以排除 `ratedToday()`，但不值得为一个数字再加分支。
- 可选（不加也行）：拆成「今天到期 / 明天到期」，用 `startOfDay` 直接算，不需要新字段。
- 卡片页打卡 `reviewDone` 仍保留——词库详情里「打卡 x/4」和卡片正面还在用。

### 5. 与现有功能的交互

| 功能 | 行为 |
|---|---|
| 同一天刷新 | `restoreQueue()` 命中（日期一致）→ 顺序原样续上，不重排 |
| 新的一天 | `mb.pos.date` 不匹配 → 按 `dueAt` 重建，到期的在前 |
| 「复习今天刷过的」 | 照常评级 → **会写新的 `dueAt`**（等于又复习了一遍）。如果希望「只看不记」，需要另加标记，默认不做 |
| 分组 / 掌握度「刷这些」 | 队列顺序按用户挑选，不受调度影响；但评级仍会更新 `dueAt` |
| 认识后 3 天内 | 不再占前排；「未学」会更快被刷完，之后每天以到期复习为主 |

### 6. 风险与兼容

- 上线当天：所有词 `dueAt` 缺省 → 全部到期 → 与今天行为基本一致，只是排序从「随机抖动」变成「稳定顺序」。
- 手机时间被改乱会导致 `dueAt` 不合理，不做额外校验（收益低）。
- 不新增 localStorage 键，不改 `wc_mobile_v1` 结构（`dueAt` 在共享的 `vocab_workbench_v1` 里）。
- **已知边界（先不做）**：App 一直不刷新、跨过 0 点继续刷，队列不会按新的一天重排。现有 `todayCount / ratedToday` 同样以天为界，跨天时数据页也会出现「今日 0 个但卡片还在队里」。概率低（需要整夜不重启），要修得在 `renderCard` 前比对 `mb.pos.date`，值得单独排一次。

## 三、验证清单

1. 三档评级后读 `store[word].dueAt`：0 → 今天 0 点；1 → 明天 0 点；2 → 3 天后 0 点（不是「此刻 + N 天」）。
2. 23:50 评级、次日早上重建队列：「认识」的词不在队列前排；「不认识」的在。
3. 把 `dueAt` 手动改成昨天/明天/0，重建队列：`0` → 昨天 → 明天的顺序。
4. 同一天刷新，仍停在同一张；把 `mb.pos.date` 改成昨天再刷新，按 `dueAt` 重排。
5. 数据页「待复习」与手动构造的到期数一致；今天评「不认识」后数字会 +1。
6. `node check_mobile.js` 语法 0 错误；分组刷词、复习今天、空态三按钮回归一趟。

## 四、明确不做的

- 「刷完自动弹自测」：会打断「滑完就收工」的节奏，且自测本来就有一键入口；需要单独评估。
- 造句、真实语料：App 补不了，保持推荐使用方式即可。

## 五、决策记录

- 间隔策略：**方案 A（固定三档）**；方案 B 的 3→7→15 递进留待观察后再定。
- 「复习今天刷过的」评级：**照常重写 `dueAt`**（复习就是一次真实回忆）。
- 落地时间：**暂不落地**，用户选择先看方案。落地时按本文档第 1–4 节改 `mobile/index.html` 的 4 处函数即可。
